# Test every Reacti feature before staging

> **Decisions (Achia, 2026-10-29).** Free options only. The repo is public, so GitHub's standard Linux and Mac machines cost nothing; the dollar figures below assumed a private repo and no longer apply. Phase 6 (paid real-device farms) is dropped. Phase 1 is built lazily: one script, no Docker, a sqlite file instead of MySQL (identical on Linux and the Mac runners, which have no service containers), seeded smoke accounts instead of test-only API routes, and no fake push sender (push already fails silently without Firebase keys). Add those only when a later phase needs them.

**Short summary.** Reacti can get to a point where almost every change has already run on realistic simulated iPhones and Android phones before Achia picks up her own iPhone. The setup is built mostly from free tools and costs about **$50 to $110 a month** in GitHub Actions minutes. The plan has three parts. First, a **throwaway copy of the Reacti server**, rebuilt from scratch for every test run inside GitHub's machines, with its own database, its own realtime (websocket) server, a fake email inbox and a fake push sender. Second, **one test tool, Patrol**, which drives the real app on an Android emulator and an iOS simulator and can tap the system pop-ups (camera, microphone, contacts and notification permission) that the current tests cannot reach. Third, a **scripted second user** who sends messages and sealed media through the server, so one simulated phone can test the full patent loop: open sealed media, mark it viewed, record silently with the front camera, upload the reaction, and the sender receives it. Android emulators can feed a real video file into the front camera, so the patent recording itself runs for real there. The iOS simulator has no camera at all, so on iOS the camera is swapped for a fake and the rest of the loop is tested. A few things a computer cannot fake still need Achia's iPhone: real camera capture on iOS, real Apple push delivery, real phone and WhatsApp calls, real Face ID, and how invite links behave after Apple's caching. The work splits into six phases, each on its own branch, and nothing changes what users see.

## Today only two device tests exist, both on Android

Reacti already has a large safety net, but nearly all of it runs in a pretend environment rather than on a device. The app has **180 test files**, all running inside Flutter's test engine with fakes standing in for the camera, the server and the realtime connection. The backend has **101 test files with about 565 tests**. The patent flow is well guarded at that level: about a dozen test files check that tapping the blur calls mark-viewed, then records, then uploads a `type: "reaction"` message (see `app/test/features/chat/widget/patent_flow_interactive_test.dart` and the backend `Patent/ReactionFlowTest`).

On a real or simulated device, coverage is thin. One file, `app/integration_test/android_device_test.dart`, holds **two tests**: it records a real clip from the emulator's front camera, and it opens the system photo picker. They run on an Android emulator in CI, next to launch-smoke and app-link checks, and that job is not yet a required check. **There is nothing on iOS simulators at all.** The "iOS integration tests" layer (3f) in the May 2026 staging plan was specified but never built. Many screens have no rendering test of their own: chat_screen, media_preview_screen, full_screen_image_viewer, the request screens, the group screens and the invite "connect" screen. Push notifications, the app badge, the call guard's native code, real Face ID prompts and live websocket delivery from the app have no device automation.

The gap that matters most for the business is simple. **Nobody has automatically run the full patent loop end to end on any device**: a real server, a real tap on sealed media, real recording, a real upload, and the sender actually receiving the reaction. Today the only proof of that chain is Achia trying it on a staging build.

## Patrol is the right single tool, with a scripted second user

Flutter's own test tool, `integration_test`, runs inside the app on a device, but by design it **"can't interact with native platform UI"**. That means it cannot tap a camera permission prompt, a notification or the Face ID sheet. Flutter's official docs point to **Patrol** by name for exactly this: permission dialogs, notifications and platform views ([Flutter docs](https://docs.flutter.dev/cookbook/testing/integration/introduction.html)). Patrol tests are written in the same language as Reacti's existing tests (Dart), so the AI agent can reuse current helpers and keys. Under the hood they are still `integration_test` tests, so the two existing Android tests move over without being rewritten. On both iOS and Android, Patrol can handle permission dialogs, open and tap notifications, open URLs, press home, switch dark mode and turn Wi-Fi or airplane mode on and off ([Patrol feature parity](https://patrol.leancode.co/documentation/native/feature-parity)). It is actively maintained: **patrol 4.10.0 and patrol_cli 4.8.0 shipped in September 2026** ([Patrol changelog](https://pub.dev/packages/patrol/changelog)).

Patrol's weakness is churn and CI flakiness. Recent minor releases renamed things in breaking ways ([patrol_cli changelog](https://pub.dev/packages/patrol_cli/changelog)), and one vendor comparison warns teams to avoid it "unless you can absorb CI debugging" ([DeviceLab](https://devicelab.dev/blog/flutter-testing-maestro-patrol-appium)). That vendor sells device labs, so treat this as an opinion. In Reacti's case an AI agent absorbs the debugging, and pinning exact versions handles the churn. The alternatives fit less well. **Maestro** drives the finished app from outside using simple scripts and handles system pop-ups well. But it cannot see Flutter's internal widget keys, so every button would need extra accessibility labels in the production code ([Maestro Flutter docs](https://docs.maestro.dev/platform-support/flutter)). It can also only seed data through a sandboxed scripting step. **Appium** adds a separate server, a second programming language and a special build, and its Flutter driver is community-maintained ([appium-flutter-driver](https://github.com/appium-userland/appium-flutter-driver)). Maestro is worth keeping in reserve for a couple of "launch the release build" smoke checks later. It is not the backbone.

For conversations, the standard low-flake pattern is **one simulated phone plus a scripted second person**. The phone is user A, driven through the real screens. User B is a few lines of test code that call the server directly to send a message, a sealed photo or a friend request, then check what arrived. Practitioners who test messaging apps make this argument directly: you "dont need to have a second device" when the second party's actions go through the server ([MIT App Inventor community](https://community.appinventor.mit.edu/t/testing-as-several-users/7146)). Each test waits for something to appear on screen rather than sleeping for a fixed time. True two-phone tests are possible, but they cost more and flake more, so they belong in a nightly run for one or two critical loops.

## A fresh test server per run beats pointing tests at staging

The tests need a server to talk to. Staging is the wrong choice. It deletes chat data older than 24 hours every hour, it is shared with Achia's manual checks, and shared environments are a well-known cause of flaky tests. Delivery Hero moved its mobile tests off shared staging for exactly these reasons ([Delivery Hero](https://tech.deliveryhero.com/mockingjay-the-ultimate-mock-server-secrets-revealed-for-mobile-apps)), and shared state is one of the main causes of flaky end-to-end tests ([dev.to](https://dev.to/how-to-dev/what-causes-end-to-end-flakiness-and-how-to-address-it-48ob)). Faking the server completely is also wrong for Reacti. A fake would skip mark-viewed, the upload and the websocket broadcast, which are exactly the parts the patent test protects. Practitioners warn that mocks "can pass while the real API is broken" ([Android UI testing cookbook](https://android-ui-testing.github.io/Cookbook/practices/network)).

So each CI run builds its own short-lived Reacti server on the same GitHub machine as the emulator. A MySQL database runs as a side container, which GitHub supports on Linux machines with a health check, so tests wait until it is ready ([GitHub Docs](https://docs.github.com/en/actions/use-cases-and-examples/using-containerized-services/creating-postgresql-service-containers)). Laravel runs with `php artisan serve`. The realtime server runs with `php artisan reverb:start`, which listens on port 8080 and has a `--debug` mode that logs every message, which is useful when a test fails ([Laravel Reverb docs](https://laravel.com/docs/11.x/reverb)). The Android emulator reaches the host computer at the special address `10.0.2.2`, and the iOS simulator uses plain `localhost` ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/maui/data-cloud/local-web-services)). The app already accepts the server address as a build setting (`--dart-define=BASE_URL=...`). The realtime host needs the same treatment.

Three outside services must be replaced, because a test server should never email real people or push to real phones. Email goes to **Mailpit**, a fake inbox with a web page and an API that tests can read ([Testcontainers Mailpit](https://golang.testcontainers.org/modules/mailpit/)). That lets the sign-up test read the real 4-digit code, since Reacti's OTP is random and has no bypass. Push notifications go to a small fake sender that writes each would-be push into a table instead of calling Google. This is needed because **Firebase has no emulator for push messaging** ([Firebase Emulator Suite](https://firebase.google.com/docs/emulator-suite)). Finally, a small set of test-only server addresses ("create a verified user", "load a scenario", "show me the pushes you would have sent") is switched on only when the server runs in a special `e2e` mode with a secret header, plus a backend test proving those addresses return "not found" in production. The existing smoke-account seeder (smoke-a and smoke-b, already friends and in a shared group) is a ready-made starting scenario.

One trap: GitHub's Mac machines **do not support side containers** ([GitHub Docs](https://docs.github.com/en/actions/use-cases-and-examples/using-containerized-services/creating-postgresql-service-containers)). So on iOS the server has to be installed directly on the Mac, with PHP from Homebrew and SQLite or MySQL. Backend CI already runs on SQLite, so that path is proven. Nobody has yet confirmed that it holds up next to a running simulator, so Phase 3 starts by proving it. If it fails, the fallback is a small, separately hosted test server that resets itself, kept apart from staging.

## Most features can be faked on simulators, and the camera splits the platforms

The table below shows, feature by feature, how each one is tested on a computer and what a simulator cannot do. The single most important row is the camera. **The Android emulator can feed the front camera from a video file** (`-camera-front videofile:face.mp4`) ([Android emulator command line](https://developer.android.com/studio/run/emulator-commandline)). That means Reacti's real recording code, the actual silent-recording path, runs end to end on Android. **The iOS simulator has no camera.** On iOS the test build swaps the camera for a fake that hands back a canned video clip. The fake slots in the way the camera plugin's own tests do it, by replacing `CameraPlatform.instance` ([camera plugin tests](https://flutter.googlesource.com/mirrors/plugins/+/04b0b4b13f59bea7b3375dbe2c5a013e6f0ed5a4/packages/camera/camera_platform_interface/test/camera_platform_interface_test.dart)). Then everything around the recording is tested for real: the blur, mark-viewed, the upload and the sender receiving the reaction.

| Feature | Android emulator | iOS simulator | Still needs a real iPhone |
|---|---|---|---|
| Patent flow (silent front-camera recording) | Real recording from a video-file camera, full loop against the test server | Full loop with a fake camera | Real Apple camera capture: start-up delay, silence, orientation, quality |
| Camera and mic permissions | Patrol taps the real prompt, or `adb shell pm grant` | Patrol taps the prompt; `applesimutils` presets camera and mic ([AppleSimulatorUtils](https://github.com/wix/AppleSimulatorUtils)) | First-run prompt wording on a real phone |
| Calls guard ("sealed media stays closed during a call") | Real simulated phone call with `adb emu gsm call` / `accept` / `cancel` ([emulator console](https://developer.android.com/studio/run/emulator-console)) | Fake "in a call" signal; CallKit does not work on the simulator ([discussion](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/65501603/is-it-possible-to-receive-calls-using-callkit-in-ios-simulator)) | Real phone call and WhatsApp or FaceTime call |
| Push notifications and tap-to-open | Fake sender plus Patrol notification tap; real Firebase push possible on Google Play emulator images | `xcrun simctl push` delivers a fake push; Patrol taps it ([simctl reference](https://tessl.io/registry/dpearson2699/swift-ios-skills/3.9.0/files/skills/ios-simulator/references/simctl-commands.md)) | Real Apple push via Firebase; iOS 26 simulators have a known token bug ([Apple forums](https://developer.apple.com/forums/thread/797507), [flutterfire #17729](https://github.com/firebase/flutterfire/issues/17729)) |
| Invite deep links | `adb shell am start -d https://...` ([adb docs](https://developer.android.com/tools/adb)), plus the existing "each app claims only its host" check | `xcrun simctl openurl` | Link behaviour after Apple caches its link file for days |
| Face ID / fingerprint app lock | `adb emu finger touch` after enrolling a fingerprint once ([emulator console](https://developer.android.com/studio/run/emulator-console)) | `applesimutils` enrol, match and no-match ([AppleSimulatorUtils](https://github.com/wix/AppleSimulatorUtils)) | Real Face ID and passcode fallback |
| Contacts sharing | Insert contacts with `adb shell content insert` ([OWASP MASTG](https://mas.owasp.org/MASTG/techniques/android/MASTG-TECH-0148/)), grant or revoke permission | `simctl addmedia` a contacts file; `simctl privacy grant/revoke contacts` | Her real address book |
| Realtime websockets | Local Reverb; the test waits for the message to appear | Same | Real mobile network handovers |
| Media picker and gallery | Push files to the emulator; Patrol picks images | `simctl addmedia` photos and videos; Patrol picks images | None material |
| Offline and reconnect | Airplane mode and network speed controls | Patrol Wi-Fi toggles; real offline needs host tools | Real weak signal |
| Login, sign-up, OTP, friends, groups, search, block, report, tour, settings | Normal screen taps; OTP read from Mailpit | Same | None material |

Two of these need small "seams" in the app: a way for a test build to swap in the fake camera on iOS, and a way to swap in a fake call-state signal. Both touch the patent area. The repo's own rules require any change there to come with an end-to-end regression test, and these phases deliver exactly that test. The fakes must only be reachable from test builds. The same goes for allowing plain `http://` to the local test server: that must be switched on only in a test build, and never by extending the existing `MyHttpOverrides` certificate bypass, which the repo already lists for removal.

## Six phases take Reacti from two device tests to full coverage

Each phase goes on its own branch, ends with a working result, and adds tests and test-only plumbing without changing anything users see. Following the "develop must always be releasable" rule, the agent asks Achia before the first merge of this initiative into develop.

| Phase (branch) | What it delivers | Features covered | Tools | Added CI cost (est.) |
|---|---|---|---|---|
| **1. Throwaway test server** (`test/e2e-backend`) | One script that boots Laravel, MySQL, Reverb and Mailpit on a CI machine; `e2e` mode with secret-gated test addresses; fixed or readable OTP; fake push sender; production-safety test | Backend side of every journey; sign-up email | GitHub Actions Linux, MySQL container, Reverb, Mailpit | Under $2/month |
| **2a. Android core journeys** (`test/android-e2e-core`) | Patrol added; the two existing tests moved over; scripted user B; tests for login, 1:1 and group chat, sending media, live websocket delivery, and **the full patent loop with real front-camera recording** | Auth, chat, groups, media send, realtime, patent flow | Patrol, Android emulator (API 34) with video-file front camera | About $5 to $10/month |
| **2b. Android native features** (`test/android-e2e-native`) | Permission prompts, call guard via simulated phone calls, fingerprint app lock, contacts seeded and revoked, invite links opened from outside, notification tap to chat, offline and reconnect | Calls guard, app lock, contacts, deep links, push tap, offline | adb, emulator console, Patrol native actions | Included above |
| **3. iOS simulator journeys** (`test/ios-e2e`, the never-built layer 3f) | Same Patrol tests on iPhone simulators; server installed on the Mac; fake camera and fake call signal; `simctl push`, `openurl`, contacts and photo seeding; Face ID match and no-match | Everything in 2a and 2b, with fakes for camera and calls | macOS 26 runner with pinned Xcode, simctl, applesimutils | About $35 to $85/month (see below) |
| **4. Screen look checks** (`test/visual-goldens`) | Picture comparisons for screens with no tests today (chat screen, media preview, full-screen viewer, profile, requests, groups), generated on Linux so Windows font differences never cause false alarms | Visual regressions, light and dark themes | Alchemist goldens ([pub.dev](https://pub.dev/packages/alchemist)) | Under $2/month |
| **5. Nightly deep run and gate** (`test/nightly-device`) | Full suite on both platforms every night; one true two-phone patent loop (emulator plus simulator); optional real Firebase push to a Google Play emulator; flake log; Android and iOS device jobs become required PR checks once green for two weeks | Everything, plus real Android push and cross-platform sender and receiver | GitHub Actions schedule | Included in the totals |
| **6. Optional real-device pass before releases** (`test/device-farm`) | A short pay-per-use run on real rented Android phones and iPhones: app launches, recording starts and the reaction uploads | Real hardware smoke; covers the "no Android phone" gap | AWS Device Farm, $0.17 per device-minute with 1,000 free trial minutes ([AWS](https://aws.amazon.com/device-farm/pricing/)) | Free at first, then a few dollars per release |

Phase 1 goes first because every later phase needs it. Phase 2a comes right after because it puts the patent loop under real device test at the lowest price. Phase 4 can run in parallel at any point. Phase 3 is the most important and the most expensive. Phase 6 is optional because Achia's staging check already covers the iPhone side. Device farms also cannot feed chosen content into the camera ([Patrol CI platforms](https://patrol.leancode.co/ci/platforms)), so they can only prove "it recorded and uploaded", never what was filmed. Avoid building on Firebase Test Lab even though it is cheap. It is deprecated and **shuts down on September 30, 2027** ([Firebase](https://firebase.google.com/docs/test-lab/migrate)).

Once all phases are in, a change moves through the pipeline like this. The agent first runs the Android tests locally on the Windows PC. The Android emulator works on Windows through the Windows Hypervisor Platform setting ([Android Developers](https://developer.android.com/studio/run/emulator-acceleration)); whether that setting is available on Windows 11 Home still needs checking with `emulator -accel-check`. iOS can never run on Windows. On every pull request, CI runs the existing unit tests, the Android device suite and the picture checks. A quick iOS subset also runs when app code changed. After the merge to develop, the nightly run covers everything on both platforms. Only then is a staging build cut for Achia.

### What it costs and why iOS is the expensive part

GitHub charges **$0.006 per minute on Linux and $0.062 per minute on macOS**, about ten times more, after a price cut on January 1, 2026 ([GitHub pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing), [GitHub changelog](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/)). Private repositories get a monthly credit of **$12 on Free or $18 on Pro or Team**, about 190 to 290 Mac minutes ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). The TestFlight staging builds already spend from that same Mac credit. The estimate below is my own arithmetic from list prices. It assumes about 80 PR test runs a month, of which about 40 touch app code.

| Item | Assumption | Monthly cost |
|---|---|---|
| Android device suite on PRs | 80 runs at 15 min on Linux | about $7 |
| iOS quick subset on app PRs | 40 runs at 15 min on Mac | about $37 |
| Nightly Android full suite | 30 nights at 40 machine-min | about $7 |
| Nightly iOS full suite | 30 nights at 25 min on Mac | about $47 |
| **Total** | before GitHub's monthly credit | **about $100** |

If that is too much, run the iOS PR subset only on PRs that touch screens, or labelled ones. That brings the total to about **$50 to $60 a month**. These are rough numbers, and the real figures will show in GitHub's billing page after the first month. Subscriptions do not pay off at Reacti's size. BrowserStack, Sauce Labs and Maestro Cloud cost about **$175 to $250 a month for each device running in parallel** ([BrowserStack](https://www.browserstack.com/pricing?product=app-automate), [Maestro](https://maestro.dev/pricing)), and a rented cloud Mac costs about €149 a month ([Scaleway](https://scaleway.com/en/pricing/apple-silicon)). Two calendar items need watching. GitHub's macOS 14 machines are scheduled for removal on November 2, 2026, so the iOS job should name `macos-26` and an exact Xcode version, a lesson this repo already learned the hard way. Separately, Android's older AEHD emulator driver on Windows ends on December 31, 2026 ([Android Developers](https://developer.android.com/studio/run/emulator-acceleration)).

### What stays manual on Achia's iPhone

After all six phases, Achia's staging check becomes short and focused instead of a full re-test. She still has to check six things. First, open a sealed photo from a second account and confirm that **a real reaction video of her face** was recorded and that the sender received it. This is the only proof of Apple's real camera path. Second, receive **a real push notification** with the app closed, then tap it into the right chat. Third, have someone **call her (phone and WhatsApp)** and confirm sealed media stays shut. Fourth, lock the app and unlock it with **real Face ID**, then once with the passcode. Fifth, open **an invite link from Messages**. Sixth, use the app for a few minutes to look for heat, slowness or anything that looks wrong. Android has no manual cover today, because Achia owns no Android phone. Phase 6, or one cheap Android phone later, closes that gap.

## Conclusion

The cheapest and strongest move is also the first one: a throwaway test server plus Android emulator tests that run the real patent recording, for under $15 a month. After that, every change to the blur, the trigger, the upload or the websocket gets checked end to end on a device before it reaches develop, something that today only happens on Achia's phone. iOS is where the money goes, because Mac minutes cost ten times more and the simulator has no camera. The iOS phase therefore mainly guards the surrounding steps (screens, permissions, push taps, Face ID logic and links), while the camera itself stays proven on Android and on Achia's iPhone.

The biggest open questions are practical, not strategic. Can the test server run reliably on GitHub's Mac machines without containers? How flaky will Patrol be on CI emulators in practice? Is the Windows Hypervisor Platform setting available on Achia's Windows 11 Home PC? Each phase is built to answer one of these early, on its own branch, before anything depends on it. The real-device step does not go away. It moves from "test everything again by hand" to a six-item check of the things only real hardware can show.
